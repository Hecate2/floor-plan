# fprec — 户型图 → 结构化建筑数据

输入一张户型图（截图 / 渲染图 / 扫描件 / PDF 转出的位图），输出**带真实尺寸（mm）的结构化 JSON**：
墙体（位置、厚度、内外墙）、门窗洞口（类型、宽度、所在墙）、房间（多边形、净面积、语义类别、是否水区）、
房间-墙体-洞口拓扑图。目标是为后续的水电布线路由、WiFi 布点、通风/散热仿真提供统一输入。

```
python -m fprec.cli example.webp -o out
# out/example.json          结构化数据（mm）
# out/example_overlay.png   校验叠加图
# out/example.svg           矢量导出
# out/manifest.json         批处理清单
```

---

## 1. 为什么不是"一把梭大模型"

先说结论，再给依据：

| 路线 | 几何精度 | 语义（房名/用途） | 工程性 | 判断 |
|---|---|---|---|---|
| A. 纯 CV（线稿 → 墙体 → 房间） | 像素级、可解释 | 无 | 稳定、可离线、可批处理 | **必须做**，是几何骨架 |
| B. 深度学习分割（CubiCasa5K / R2V / UNet / YOLO-seg） | 好，但受训练集风格限制 | 有类别但粗 | 需权重+GPU/耗时，风格迁移未验证 | **推荐做**，作为 A 的先验/补漏 |
| C. 多模态大模型直接出 JSON | 差（坐标不可信） | 强（房名、用途、常识） | 每次调用有成本、不稳定 | **只让它干语义** |
| D. 商业 API（Tectly / RasterScan / CubiCasa） | 好 | 好 | 按次计费、数据出域 | 量大时的对照基线 |

调研依据（2024–2025）：

- **CubiCasa5K** 仍是事实标准数据集（5000 张、80+ 细类、多边形标注），官方模型沿用 **Raster-to-Vector** 的多任务结构（分割 + 关键点热图 → 矢量化）。官方权重托管在 Google Drive，需要按仓库说明下载。
- 现成可用的预训练模型：`Yytsi/floorplan-to-3d-walls`（ResNet-34 + UNet，4 类 floor/wall/door/window，CubiCasa5K val mIoU 0.983，CPU 可推理，512×512 letterbox）；`FloorCAD` 系列（YOLOv8n-seg，输出 wall/opening/stairs 实例掩码）。
- 户型图分割的新工作（如 MitUNet，arXiv 2512.02413）仍在解决"细墙、几何精度"这类问题，说明单靠分割不够，**后处理矢量化才是精度关键**。
- VLM 侧：*Vision Language Models Can Parse Floor Plan Maps*（DeFazio et al., 2024/2025）证明 VLM 能读出房间名/连通关系；但 **Blueprint-Bench**（Andon Labs, 2025）显示把照片还原成平面图时，人类相似度 0.547、GPT-5 仅 0.431 —— VLM 的**坐标/尺度不可信**，语义可信。
- 已有 VLM 微调尝试（如 `qwen25-vl-3b-floorplan-sft` / GRPO 版）在做"图 → 结构化 JSON"，可作为 C 路线的加速器，但同样需要 B/A 做几何约束。

所以本工具采用 **A 为核心 + C 只补语义 + B 可插拔** 的混合架构。关键设计：
**几何永远是确定性的、可复现的、可校验的；大模型/OCR 只提供"这里叫什么、这间多大"这类先验。**

## 2. 架构

```
                    ┌──────────────── 语义层（可插拔） ────────────────┐
 图片 ──► 预处理 ──► │ OCR(RapidOCR/tesseract) → 房名、面积、尺寸链数字 │
        (灰度/去斜)  └───────────────┬────────────────────────────────┘
                                      │ 只喂"先验"，不喂几何
                                      ▼
         ┌────────────────── 几何层（确定性 CV） ──────────────────┐
         │ 1 墙体掩码：深色 + 形态学开运算去细线 + 连通域过滤        │
         │ 2 矩形分解：最长行程生长法，把正交墙拆成轴对齐矩形        │
         │ 3 墙段建模：共线合并 + 端点吸附 + 厚度统计（内外墙判别）  │
         │ 4 洞口：同墙线上相邻墙段之间的空隙 → 门/窗/开敞洞口       │
         │ 5 房间：两级分割（见下）                                  │
         │ 6 比例尺：尺寸标注链 OCR → mm/px（最小二乘 + 鲁棒中位数） │
         └───────────────────────────┬─────────────────────────────┘
                                     ▼
              JSON(mm) / 叠加图 / SVG + 自检告警（面积对不上就报警）
```

### 2.1 墙体矢量化（而不是"直接拿黑色像素当墙"）

1. `gray < 70` 取深色 → `5×5` 开运算，厚度不足 5px 的线（文字、门弧、箭头）被抹掉；
2. 连通域按面积过滤；
3. **矩形分解**：反复找当前掩码里最长的水平/垂直行程，沿垂直方向按 ≥85% 覆盖率生长成一个矩形，挖掉，继续。这样 L 形、T 形墙会被拆成若干轴对齐矩形；
4. 矩形 → 墙段（长边为走向，短边为厚度），按"长度 ≥ 1.8×厚度、厚度 ≥ 3px、厚度 ≤ 2.6×中位厚度"过滤掉门弧、箭头、涂黑的家具；
5. 共线合并 + 端点聚类吸附（±4px），得到轴网化墙段。

本例效果：33 段墙，对原始墙体像素覆盖率 **98.3%**（改前 62.6%，原因是最长行程只找水平的，竖直墙被漏掉）。

### 2.2 洞口 = 墙线上的"空隙"

同一墙线上相邻两段墙之间的空隙即洞口，按"是否临建筑外轮廓 / 宽度（mm）"分为 窗 / 门 / 开敞洞口。
比"检测门的圆弧符号"稳健得多——不依赖绘图习惯（弧线、矩形门扇、推拉门都能覆盖）。

### 2.3 房间 = 两级分割

难点：门洞是开的，窗洞也可能是开的，一次性 flood fill 一定漏。

1. **种子阶段**：屏障 = 所有墨线 + 膨胀后的墙 + 洞口封堵（封堵矩形再加 4px，否则会从窗线旁的窄缝绕过去）。
   膨胀半径取门宽的一半（约 `2.25×墙厚`），门洞被"虚拟墙"封住 → 每个房间得到独立种子；
2. **生长阶段**：种子沿"只被墨线阻挡"的自由空间测地漫延，长回真实墙边 → 面积不受膨胀影响；
3. **补面积**：深色实心块（衣柜、床、洁具）不是墙，把质心落在房间多边形内的实心块并回房间，避免面积被家具吃掉；
4. **去假房间**：低"贴墙率"的区域（水印、阴影）并给邻接房间；既没有门窗、也读不到房名的封闭小块（床/沙发/餐桌围出来的坑）同样并回邻居——
   判据是语义不是尺寸，因为真房间一定连着别的空间或写着房名；
5. 大图上先 1/4 分辨率生长、再全分辨率精修，3000px 的图从 22 s 降到 13 s。

### 2.4 比例尺（这是最容易做错的一步）

尺寸链上每个数字写在它那一段的正中间，于是

```
s_i = (w_i + w_{i+1}) / (2 · d_i)     d_i = 相邻两个数字的中心距(px)
```

不需要检测刻度线，对多对取鲁棒中位数即可。`example.webp` 上读出 2 条标注链、7 个相邻对，
得到 **22.32 mm/px，离散度 0.7%（置信度 0.95）**；6 张图里 5 张都能这么标定。
兜底顺序：尺寸链 → 图上标注面积拟合 → 外墙 240mm 经验值（并明确告警 + 置信度 0.25）。

### 2.5 多平面（1F / 2F 并排在一张图里）

用**墙体**（不是墨线，尺寸链是细线会被排除）膨胀后聚类，得到几块互不相邻的平面；
每块外扩 60px 以保住自己的尺寸链，各自独立标定比例尺、独立分割房间，最后合成 `levels[]`。

### 2.6 自检（比精度更重要）

- 每间房的"计算面积 vs 图上标注面积"对比，偏差 >15% 直接进 `diagnostics.warnings`；
  （一块区域里有多个面积标注时按求和核对——开敞空间被合并时面积仍应吻合）
- 一块区域里读出多个房名 → 判定欠分割并告警；
- 比例尺来源与置信度、OCR token 数、覆盖率全部写进 JSON，方便批量筛查哪张图需要人工复核。

## 3. 实测（6 张真实户型图 + 1 张合成线稿）

`python -m tests.eval_areas` 会把每张图上"计算面积"与"图上标注面积"逐间对比：

```
file             plans rooms   scale method         paired  medAE  <10%
example.webp         1     9   22.32 dimension_chain      7   5.9%   57%
example2.jpg         1    12   22.34 dimension_chain      9   5.0%   78%
example3.jpg         1     7   18.46 default_wall         0   0.0%    0%
example4.jpg         1     7   18.78 dimension_chain      7   8.1%   71%
example5.jpg         2    13   22.52 dimension_chain     13   4.1%   92%
example6.jpg         1    15   10.71 dimension_chain     12   7.5%  100%

合计 48 个带标注的房间：中位绝对误差 6.0%，≤10% 83%，≤20% 92%，≤30% 98%
```

| 图 | 特点 | 结果 |
|---|---|---|
| `example.webp` | 渲染图，家具/木纹/水印，四边尺寸链 | 22.32 mm/px，9 间，30 段墙 |
| `example2.jpg` | 带斜切角（八角飘窗），链上有小段尺寸 | 22.34 mm/px，12 间；斜墙退化成折线 |
| `example3.jpg` | **低清、无尺寸、无面积标注** | 只能按外墙 240mm 反推 18.46 mm/px（告警，误差未知） |
| `example4.jpg` | 渲染图，有尺寸链 | 18.78 mm/px，7 间 |
| `example5.jpg` | **一张图并排两张平面（1F / 2F）** | 自动切成 2 块独立平面：L1 7 间 / L2 6 间，比例尺各自标定 |
| `example6.jpg` | 3000×2250 大平层，20 个空间、挑空 | 10.71 mm/px，15 间，114 段墙，13 s |
| `out/synthetic.png` | 合成线稿，真值已知 | 比例尺误差 −0.3%，四间房面积误差 +9/+3/+2/+1% |

### 3.1 关键工程结论

1. **比例尺是整个精度的天花板**。6 张图里 5 张能从尺寸链标定（离散度 <3%），
   剩下那张没标注的只能告警——**宁可报警也不要编一个数**。
2. **标注面积是免费的自检金标准**。图上写着的面积被 OCR 出来后，逐间对账，
   偏差 >15% 直接进 warnings；这也是批量筛选"哪张图要人工复核"的依据。
3. **多平面必须自动拆**。中介图经常把 1F/2F 并排放，当成一张图处理会把两层缝在一起。
   现在用"墙体聚类 + 外扩 60px 保留尺寸链"来切，每块独立标定比例尺。
4. **大图要控成本**。3000px 的图原来 22 s，做了三件事降到 13 s：
   多分辨率测地生长（1/4 分辨率生长 + 全分辨率精修）、连通域操作限制在 bbox 内、
   大图在 1600px 掩码上做矩形分解再换算回原坐标（覆盖率仍 95%）。

### 3.2 已知失败模式（工具会自己报警）

1. **阳台/大窗洞把相邻房间连成一块**（如 `example.webp` 的阳台B ↔ 卧室C）：窗洞跨整面墙时两侧没有可配对墙段 → 告警"区域内含多个房名"。
2. **家具/隔板线把房间拆成两块**（储物间）→ 面积告警。已加"既无门窗又无房名就并回邻居"的规则，能吃掉大部分家具坑，但贴着墙的沙发/床仍可能残留。
3. **大平层容易欠分割**（`example6` 的客厅+挑空+书房连成一片）。
4. 门窗分类是启发式（临外墙 + 墙线上玻璃线密度），个别窗会被判成门。
5. 无尺寸链的图（`example3`）比例尺不可信，只能靠 hints 或人工。

## 4. 接口设计（为什么这样输出）

```jsonc
{
  "schema": "fprec/0.2",
  "units": "mm",
  "coordinate_system": {"origin": "plan_bbox_min_corner", "x": "right", "y": "down"},
  "levels": [{
    "id": "L1", "name": "F1", "origin_px": [0, 0],
    "scale": {"mm_per_px": 22.316, "method": "dimension_chain", "confidence": 0.95},
    "wall_height_mm": 2800,
    "outline": [[x, y], ...],
    "walls":    [{"id": "W1", "a": [x, y], "b": [x, y], "thickness": 245, "kind": "exterior"}],
    "openings": [{"id": "O3", "type": "window", "host_wall": "W10",
                  "a": [...], "b": [...], "width": 982, "sill": 900, "height": 2300}],
    "rooms":    [{"id": "R4", "label": "卧室A", "category": "bedroom", "wet_room": false,
                  "polygon": [[x, y], ...], "area_m2": 10.51, "area_printed_m2": 11.2,
                  "walls": ["W3", "W6"], "openings": ["O2"], "neighbors": ["R1"],
                  "centroid": [x, y], "confidence": 0.82}]
  }],
  "graph": {"nodes": [{"id": "L1:R4", "level": "L1", "category": "bedroom", ...}],
            "edges": [{"a": "L1:R3", "b": "L1:R6", "via": ["O5"], "kind": "door"}]},
  "diagnostics": {"warnings": [...], "stats": {...}}
}
```

- 一张图里并排几张平面 → `levels` 有多个元素；单层时额外保留扁平的 `level` / `scale` 字段方便直接取用。
- 所有坐标都是**该层自身**的 mm（原点为轮廓最小角点），跨层比较请加上 `origin_px × mm_per_px`。

刻意保留的东西：`area_printed_m2`（对账用）、`confidence`（每元素可信度）、`wet_room`（水区，决定给排水路由）、
`graph`（管路/网线走向的搜索空间）、`diagnostics.warnings`（批量质检入口）。

**对接下游还缺的信息**（下一步要补，见 §6）：墙高/墙材质（WiFi 衰减）、楼板/层高（CFD）、
设备点位（厨卫洁具、强弱电箱）、门的开启方向、地漏/立管位置。

## 5. 目录结构

```
fprec/
  config.py       参数（阈值、默认建筑尺寸）
  geometry.py     读图/去斜/墙体掩码/矩形分解/墙段合并吸附
  structure.py    洞口检测、外轮廓、两级房间分割、碎块合并、多边形正交化
  scale.py        比例尺：尺寸链拟合 / 标注面积拟合
  text.py         OCR 层（RapidOCR 优先，tesseract 兜底）
  model.py        输出数据模型与 JSON schema（多楼层）
  pipeline.py     多平面拆分 + 端到端编排 + 自检
  viz.py          叠加图 / SVG
  cli.py          批量命令行
tests/
  make_synthetic.py   生成带真值的合成线稿（跨风格回归）
  eval_areas.py       批量对比"计算面积 vs 图上标注面积"
  test_smoke.py       冒烟测试
```

uv venv --python 3.12 .venv && source .venv/bin/activate

可选：`brew install tesseract` + `tesseract-lang`（有 `chi_sim` 时自动启用中文）。
RapidOCR（`rapidocr-onnxruntime`）自带方向检测，竖排尺寸链也能读，**推荐装**。

### 人工 / VLM 校对回路

`--hints hints.json` 可以喂语义先验，几何仍由 CV 决定：

```json
{ "scale_mm_per_px": 22.3,
  "rooms": [ {"label": "卧室A", "area_m2": 11.2, "at": [350, 250]} ] }
```

推荐工作流：`批量跑 → 看 warnings（面积偏差/多房名/无比例尺）→ 只把有问题的图交给 VLM 或人工出 hints → 重跑`。
这样昂贵的大模型调用只发生在少数图上，且**几何结果仍然可复现**。

## 7. 下一步（按性价比排序）

1. **补洞口检测的兜底**：整面墙都是窗（两侧无墙段可配对）时，用"墙线上的细双线/细三线"符号检测窗；门用"弧线 + 门扇直线"符号交叉验证。
2. **房间合并/拆分规则化**：相邻房间共享边界若完全没有墙像素 → 合并（开放厨房）；一块区域里读出多个房名 → 用这些房名做种子切开（`--split-by-labels` 已实现，但生长用欧氏距离时边界会在开敞空间里乱切，需要"墙优先"的距离场）。
3. **接入 DL 分割**（B 路线）：`Yytsi/floorplan-to-3d-walls`（CubiCasa5K UNet）或 `FloorCAD` YOLO-seg 出 wall/door/window 概率图，与本工具的几何后处理串联——分割负责"哪里有墙"，矢量化负责"墙在哪、多厚、多长"。风格差异（渲染图 vs 线稿）正好由两路互补。
4. **多楼层堆叠**：并排的两层已经能分别识别（`levels`），下一步做"上下层对齐"——用外墙/楼梯间把 L1 与 L2 叠到同一坐标系，才能算竖向管井与上下层传热。PDF 还需按页/图层拆，剔除立面与总平面页。
5. **面向仿真的补充层**：墙体材质与高度、窗台/窗高（已给默认值）、门开启方向、设备点位。CFD 与 WiFi 都要"洞口尺寸 + 墙厚 + 材质"三件套，本 schema 已留位。
6. **回归集扩到 50–100 张**：目前 6 张真实图 + 1 张合成的回归已能覆盖"渲染图/线稿/无标注/多平面/大平层"五类；
   再补人工标注（房间多边形、洞口）就能算 mIoU / 房间边界 F1 / 洞口召回，而不是只看面积误差。

## 8. 已知局限

- 渲染图里的木纹、阴影、水印会污染"墨线"，目前用阈值 + 贴墙率过滤，换风格需要重新标定阈值（`config.py` 已把阈值显式化）。
- 斜墙/弧形墙会退化成台阶状多边形（`orthogonalize` 只做正交吸附，不对斜边做重建）。
- 一套图一个比例尺；图上没有尺寸链且没有面积标注时只能按墙厚猜，误差可能 >30%（会告警）。
- 并排的多平面能自动拆；但**同一张图里上下叠放**、剖面图、总平面图不处理。
- 面积口径是"净使用面积"（墙内表面），与图上标注（多为墙中线或含墙）本来就有 3–8% 的系统差，评估时请用中位误差而不是单间绝对值。
